# 实施计划：重基线、插件化与验收

- 配套：[01-现状分析.md](./01-现状分析.md)、[02-解耦改造方案.md](./02-解耦改造方案.md)
- 目标基线：上游 `dsh-v0.2.2-rc.3`（`39163dd30f`）
- 计划口径：1 人日 = 1 名熟悉 DSH 的工程师 1 个工作日；估算含自测，不含等待上游 PR 的时间
- 前置决策：D1–D5 已于 2026-11-14 确认（右侧栏、Session 级终端、采用官方浏览器与桌面、暂不发布 npm），见 [02 §3.2](./02-解耦改造方案.md)

## 1. 路线选择

| 方案 | 做法 | 冲突面 | 工期 | 风险 | 结论 |
|---|---|---|---|---|---|
| A. 直接 merge 上游 | `git merge upstream/master` 到 `custom/main`，逐个解决 211 个冲突文件 | 211 文件 + 6 个同路径新增 + `apiproxy`/details 面板/桌面壳三处架构替换 | 4–8 周，且结果仍是「深度耦合」 | 高：解完冲突仍需二次重构；`apiproxy` 已不存在，等于重写 | 不采用 |
| B. 重基线 + 插件化（推荐） | 新建纯净基线，旧线冻结；功能逐个以独立插件移植 | 新代码几乎零冲突；旧代码仅作参考 | 7–11 周（见 §4） | 中：取决于 G1/G2 PoC | **采用** |
| C. 渐进混合 | 先重基线，再在原分支上逐个删/移功能 | 同 B，但保留双线更久 | 8–12 周 | 中：双线维护成本 | 可选（团队人力充足时） |

选择 B 的关键理由：任务 2 要求「完全解耦」、任务 3 要求「独立插件」。方案 A 的终点仍需做方案 B 的工作，且把 3 个月的上游架构变更与 6.8 万行定制代码混在一次合并里。

### 5.1 基座仓门禁（必须长期为绿）

git fetch upstream

  package.json pnpm-lock.yaml tsconfig.base.json tsconfig.host.json tsconfig.client.json

# 2) 无定制符号
! rg -n '@nange|nange-' packages apps

# 3) 上游门禁
pnpm run typecheck

## 6. 降级路径（PoC 失败时）

| 失败点 | 降级方案 | 影响 |
|---|---|---|
| G1 树外 Typert 生成不可行 | 在基座仓用一个**不改源码**的旁路构建：插件源码放 `extensions/`，通过独立 `tsconfig.extensions.json` 与一次性生成脚本产出 artifacts，构建后发布到插件仓；运行期仍按树外安装 | 解耦度 90%：开发期依赖基座仓构建，发布物独立 |
| G2 树外 client bundle 不可行 | 在基座仓内构建 client 产物并随插件包发布；插件仓只做源码与发布 | 同上 |
| 两项都不可行 | 先交付纯 Host 工具插件；编辑器/Git 面板暂缓，向上游提 seam PR | 功能延期，但基线升级与终端/浏览器/桌面解耦仍可完成 |
| 桌面插件管理不可用 | 提供预置 profile 包（含插件依赖的离线目录） | 安装体验下降 |

## 7. 风险登记与应对

| 风险 | 触发信号 | 应对 |
|---|---|---|
| 上游基线自身测试不稳 | P1 出现非本仓库原因失败 | 固定到最近通过的门禁提交；记录已知失败清单，CI 排除 |
| 依赖安装慢/被墙 | `pnpm install` 超时 | 配镜像；缓存 `node_modules`/pnpm store；Electron 镜像 |
| 上游 `rc` 继续变动 | 期间发布新 rc | 冻结到 `0.2.2-rc.3`；新 rc 只记录差异，不中途切换 |
| 产品回调 D1–D5 | 后续产品决策变化 | 按 §6 降级；重新估时并更新计划 |
| 旧功能回归 | 对照脚本差异 | 逐功能开关；保留旧分支可回滚 |
| 桌面签名/公证阻塞 | P6 打包失败 | 先出未签名内部包；签名单独排期 |
| 人力被抽调 | 里程碑连续延期 | 优先保 P0–P3（基线+SDK+试点），P4/P5 可裁剪范围 |
